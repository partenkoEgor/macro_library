# Расшифровка макросов для выгрузок

Актуально на 20.10.2026. Сверено с последними версиями всех 13 макросов, которые прислали 20.10: `Monitoring_Нагрузка` (версия 17.10.2026), `Monitoring_Зависшие_72ч` (13.10.2026), `Approved_Фильтр1_v3` (3.1.4), `Approved_Перенос2_v3` (3.1.0) и остальными. Код лежит в `macros/`.

## Общее для всех макросов

- **Исходная выгрузка не меняется.** Ни один макрос не пишет в лист с исходными данными, результат появляется на отдельных листах.
- **Свои листы макрос пересоздаёт при каждом запуске.** Хранить на них свои данные нельзя. Исключения: `Упорядоченный список` (TTR_FTT) и `Результат` (Цепочки статусов) обновляются на месте, остальное содержимое листа не трогается.
- **Кнопки «Копировать»** копируют только блок значений для вставки в рабочую таблицу. Заголовки и итоговые строки видны для контроля, но в копирование не входят.
- Пороги «Nч+» везде означают «N часов и больше».

## 1. Monitoring_Нагрузка

Файл: `macros/Monitoring_Load.bas`, версия 17.10.2026.

**1) Название.** `Monitoring_Нагрузка`, объединённый макрос нагрузки и зависших тикетов. Заменил старые `Нагрузка_API`, `Общая_нагрузка_PSP`, `Общий_мониторинг_BT_M_SMP`, `Monitoring_Зависшие_L1`, `Нагрузка_и_зависшие_Fraud` и `Зависшие_по_Гео`.

**2) Функция.** За один запуск по общей выгрузке `Report` считает нагрузку и зависшие тикеты по API, PSP, BT M, SMP M, L1 и Fraud. Готовит 5 цифр для промежуточных отчётов 12:00 и 19:00, текст вечернего отчёта и контроль: какие тикеты выгрузки не попали ни в один показатель. Фильтры пресетов (департаменты, Ticket type, Agent ID, статусы, гео, рефералы) повторяются в коде, поэтому выгрузку заранее фильтровать не нужно.

**Как определяется страна тикета.** У каждого блока свой список стран. Если `Country` тикета входит в список блока, берётся она. Если нет, страна определяется по `Ticket currency` (AZN → Azerbaijan, EGP → Egypt, TRY → Turkey и т. д.). Если и по валюте страна не из списка блока, тикет в этом блоке не считается. Валюты USD, EUR, JOD и ILS страну не определяют. Пример: Russia + AZN считается как Azerbaijan, Russia + USD не считается.

**3) Что происходит с выгрузкой.**
- Лист `Report` не меняется. Если его нет или в нём нет обязательной колонки, макрос останавливается и показывает список недостающих колонок.
- Создаётся лист **`Фильтрация`**: 26 нужных колонок из `Report`. В `From` значения `Through Customer Support` / `By Customer Support` заменяются на `PS`, а `By yourself` / `By customer` на `User`. `Processing time` пересчитывается в часах от **самой поздней `Processing date` в файле**, поэтому результат не зависит от времени запуска.
- По листу `Фильтрация` строятся листы:

| Лист | Что на нём |
|---|---|
| `Нагрузка L2` | **API** (35 гео): Team B (Turkey, Azerbaijan, Bahrain, Jordan, Oman, Saudi Arabia, Somalia, со своими рефералами) и Team A. Депозиты и выводы по статусам New / Information provided / Review of stalled request / Awaiting response from PS / In progress (awaiting PS response) / Approval of compensation, плюс Buffer. У Bahrain статусы New, Information provided и Review of stalled request уходят в L1 и здесь не считаются. **PSP** (5 гео, Mena 1x и Buffer): депозиты и выводы по 5 статусам. **BT M** Mena 1x и Mena Leads 1x (34 гео, Agent ID 279, 17 рефералов): Received 189, Received (Fraud) 236, Approved 177, Create new transaction 251, Credited to another account 179, Revision needed 238, In progress 240. **BT M L2/L1** (14 гео, `BankTransferAgent #279`): 7 депозитных статусов 183 / 187 / 193 / 195 / 197 / 201 / 255. **SMP M** (13 гео, Mena 1x / Mena Leads 1x / Buffer, Agent ID не ограничивается): 7 статусов. |
| `Нагрузка L1` | BT M, Agent ID 279, Mena 1x и Mena Leads 1x, 22 гео: депозитные и выводные статусы L1, PT 24 ч и 48 ч. |
| `Нагрузка Fraud` | Mena 1x и Mena Leads 1x: нагрузка и зависшие от 24 ч по 5 фрод-статусам (User spamming, Two users, Fake file, Fake file (Fraud), Revision needed (Fraud)) и блок «Ожидание пользователей» (Awaiting BS, Awaiting video). |

SMP M: Sent for processing 72h+, New request 72h+, In progress 24 ч, PT 12 / 24 ч. Ниже API, API без гео L1 и PSP: In progress / New / Customer provided additional info / Revising 12ч+ и 24ч+ (только наши пары «гео + реферал»). |
| `ЗТ по ГЕО BT M,SMP M,PSP` | Зависшие от 24 ч по гео отдельно для BT M, PSP и SMP M, плюс разбивка по статусам и рефералам. |
| `ЗТ по ГЕО API` | Гео-таблица API / PSP: 36 гео (35 + Jamaica, пока она есть в рабочей таблице), 68 связок «гео + реферал», блок «не наши гео / рефералы» и список тикетов. |
| `Сводная` | 5 чисел для промежуточного отчёта 12:00 и 19:00 МСК: BT M 6 основных статусов (M1x), то же (ML1x), API Team A, API Team B, PSP Team B. Цифры BT M берутся из готовых итогов `Нагрузка L2` без In progress, поэтому совпадают с ней. |
| `Вечерний отчет` | Готовый текст вечернего отчёта для чата. Справа от «/» стоят вечерние цифры, их считает макрос. Слева от «/» стоят «0», их нужно заменить утренними значениями вручную. Строки «Дата», «Создано тикетов», «Выводы», «Чат 72», «Ожидают ответа», «Массовый Approved», «Ошибка - Статус» заполняются вручную. Одна кнопка копирует весь текст. |
| `Неиспользуемые тикеты` (новый, последний лист) | Ticket ID из выгрузки, которые не вошли ни в один выводимый показатель. Сверху их количество и сводка по Ticket type / Country / Department / Status / External Status, ниже полный список строк, по одной на Ticket ID. |

- Листы расставляются по порядку: `Report`, `Фильтрация`, `Вечерний отчет`, `Сводная`, `Нагрузка L2`, `Нагрузка L1`, `Нагрузка Fraud`, `Зависшие тикеты`, `ЗТ по ГЕО API`, `ЗТ по ГЕО BT M,SMP M,PSP`, в конце `Неиспользуемые тикеты`. В конце открывается `Нагрузка L2`.
- Итоговое сообщение показывает контроль: сколько уникальных Ticket ID в выгрузке, сколько использовано хотя бы раз, сколько не использовано, и разбивку по листам.

## 2. Monitoring_API_BT_M_PSP_SMP

Файл: `macros/Monitoring_API_BT_M_PSP_SMP.bas`, обновление октября 2026.

**1) Название.** `Monitoring_API_BT_M_PSP_SMP`, количество тикетов по направлениям API, BT M, PSP и SMP.

**2) Функция.** Считает тикеты каждого направления в разрезах: депозиты и выводы, источник (User / PS), VIP, департаменты, гео, рефералы. Направление определяется по `Ticket type`: `API`, `BT M`, `PSP`, `SMP M` (для SMP ещё агент SendMePay, пустой Agent допускается). Правила отбора:
- **во всех четырёх отчётах** считаются только страны из актуального списка своего листа: API 36, BT M 34, PSP 5, SMP 13 (добавлен Djibouti). Страны не из списка не попадают ни в ИТОГО, ни в рефералы;
- Rolsbet исключён полностью и в API, и в BT M;
- в PSP не считается Tunisia;
- в API реферал `in.1xbet.com` учитывается только для Турции, `1xbet.latam` только для Ямайки (способ оплаты Lynk) и Гватемалы (GT Continental, Banrural, Banco Industrial, BAC, Zigi);
- VIP: `Type` = VIP, VIP-casino или VIP-hybrid.

**3) Что происходит с выгрузкой.**
- Активный лист с **сырой** выгрузкой не меняется. Запускать нужно именно на сырой выгрузке: макрос ищет в `From` значение `by customer`, а на уже отфильтрованных листах все тикеты будут посчитаны как PS.
- Создаются 4 листа по порядку: **`API`**, **`BT M`**, **`PSP`**, **`SMP`**. На каждом:
  - сводка «Депозиты (User / PS), Выводы (User / PS), VIP, ИТОГО» по департаментам. На API это MENA 1x, Mena Leads 1X и Buffer, на BT M это MENA 1x и Mena Leads 1X, на PSP и SMP только MENA 1x;
  - блок GEO и блок рефералов (API 17 рефералов, BT M 15, PSP и SMP 14);
  - кнопки «Копировать» над каждой колонкой сводки (без ИТОГО), над GEO и над рефералами.
- Если для листа нет нужной колонки (`Payment method` для API, `Agent` для SMP), этот лист не создаётся, но в конце всё равно может появиться «Готово!».

## 3. Monitoring_Зависшие_72ч

Файл: `macros/Monitoring_Stuck72h.bas`, версия 13.10.2026. Раньше назывался `Monitoring_SFP_SMP_NR72ч`.

**1) Название.** `Monitoring_Зависшие_72ч`, тикеты, которые висят 72 часа и больше в статусах Sent for processing и New request (BT M и SMP M).

**2) Функция.** Находит тикеты, которые висят 72 часа и больше:
- **BT M:** `Ticket type` = BT M, статусы `Sent for processing (M)` и `New request (M)`;
- **SMP M:** `Ticket type` = SMP M, департаменты Mena 1x / Mena Leads 1x / Buffer, 13 стран (Egypt, Mauritania, Sudan, Honduras, Nicaragua, South Sudan, Paraguay, Qatar, UAE, Panama, Canada, Guatemala, Djibouti), 14 рефералов, статусы `Sent for processing` и `New request`. Agent и Agent ID больше не ограничивают отбор.

**3) Что происходит с выгрузкой.**
- Исходный лист не меняется. Если в выгрузке нет колонок `Ticket type` или `Department`, макрос останавливается до каких-либо изменений. Если запустить с итогового листа, макрос попросит перейти на выгрузку.
- В результате остаётся **один лист `Зависшие 72ч+`** с четырьмя блоками «Гео / Ticket ID / Subagent»: Sent for processing (M) 72h+, New request (M) 72h+, SMP Sent for processing 72h+, SMP New request 72h+. Если тикетов нет, в блоке написано «Нет тикетов».
- Промежуточные листы (`Filtered` и 4 листа со списками) макрос создаёт для расчёта и сам удаляет. Листы прошлых версий (`SMP подсчет 72h+`, `Для копирования`) тоже удаляются. Отдельного листа со счётчиками SMP больше нет.
- `Processing time` считается **от текущего времени** (`Now`), поэтому результат зависит от момента запуска.

## 4. Monitoring_Выводы

Файл: `macros/Monitoring_Withdrawals.bas`.

**1) Название.** `Monitoring_Выводы`, мониторинг выводов BT M и SMP M.

> Используйте версию из библиотеки: в ней из геофильтра убраны Dominican Republic и Papua New Guinea (подтверждено 20.10.2026). В рабочей копии, присланной 20.10, они ещё есть, поэтому модуль нужно заменить.

**2) Функция.** Считает выводы Mena 1x и Mena Leads 1x по статусам:
- **BT M** (тип `BT M`, агент BankTransfer…): 238 Review required, 205 Money not sent, cancel, 175 Adjust payment amount, 185 Limit reached on the recipient side, 191 Recipient details incorrect, 199 Request for payment statement, 203 Sent. Статусы 185 / 191 / 199 / 203 считаются только по нужным странам: Azerbaijan, Afghanistan, Bolivia, Guatemala, Honduras, Iran, Canada, Nicaragua, Panama, Paraguay, Taiwan, Kyrgyzstan, Jamaica. Остальные статусы считаются по всем странам.
- **SMP M** (тип `SMP M`, агент SendMePay): 81 Revision needed, 53 Money not sent, cancel, 38 Adjust the payout amount.

Старые названия статусов тоже распознаются.

**3) Что происходит с выгрузкой.**
- Исходный лист не меняется. Если запустить с листа `Результат` или `Фильтр`, макрос попросит перейти на выгрузку.
- Создаётся **`Фильтр`**: только подошедшие тикеты, 15 колонок (Department, Ticket type, External Status, From, Transaction Status, Transaction ID, Check amount, Subagent, Payment date, пустой разделитель, Ticket ID, Country, Processing time, Internal comment, Agent). Тикеты с `Transaction Status = rejected` стоят сверху. В `From` значение `Through Customer Support` заменяется на `L1`, а `By yourself` на `User`. `Payment date` приводится к дате. Кнопка в `K1` копирует Ticket ID отклонённых.
- Создаётся **`Результат`**: BT M (сумма в B4, 7 статусов в B5:B11) и SMP M (сумма в B16, 3 статуса в B17:B19). Кнопки копируют `B5:B11` и `B17:B19`, суммы не копируются.

## 5. Approved_Фильтр1_v3

Файл: `macros/Approved_Filter1_v3.bas`, версия 3.1.4. Первый шаг пары Approved.

**1) Название.** `Approved_Фильтр1_v3`, подготовка тикетов Approved (M) к сверке с админкой.

**2) Функция.** Для каждого тикета определяет номер транзакции и готовит список Transaction ID для загрузки в админ-панель.
- Если `Transaction ID` заполнен, берётся он.
- Если пуст, макрос ищет 11-значный номер в `Internal comment`. Отбор консервативный, сомнительные случаи уходят на ручную проверку. Номер отклоняется, если он начинается с нуля, является хвостом дробного числа или совпадает с другим полем строки (кошелёк, номер перевода, ID пользователя). На проверку также уходят строки с несколькими разными кандидатами и строки, где номер стоит посреди свободного текста без метки (например, «confirmed in complaint N»). Номер после фразы подтверждения агента и короткий комментарий вида «23340367235 already confirmed» принимаются.
- Один номер у **разных** пользователей всегда уходит на проверку. Один номер у одного пользователя: в работе остаётся один тикет, остальные уходят на проверку со ссылкой на основной.
- Строки без номера и без кандидатов отбрасываются.

**3) Что происходит с выгрузкой.**
- Исходный лист не меняется. Листы прошлого прогона (`Фильтр`, `Источник`, `На проверку`, `Отчёт`, `Из выгрузки`, `Из комментария` и старые служебные) удаляются.
- **`Фильтр`** (вставляется перед выгрузкой): строка 1 под кнопки, заголовки во 2-й строке, колонки A–AA. Пустые ADM-колонки и `Transaction status` заполнит второй макрос. Служебные колонки: «Источник номера» (Выгрузка / Комментарий B2 / D …), «Кандидаты из комментария», «Примечание». `From` приводится к `PS` / `User`. Кнопки «Копировать 1–5000», «5001–10000» и т. д. копируют Transaction ID блоками до 5000 штук для админки.
- **`На проверку`**: Ticket ID, Date created, Country, User ID, Check amount, Ticket currency, Subagent, Internal comment, кандидаты и причина. Этот лист нужно просмотреть до загрузки в админку.
- **`Отчёт`**: цифры прогона в раскладке ежедневного отчёта (строки 3–15): всего тикетов Approved (M), с транзакциями, без транзакций (формула `=B3-B4`), прошло на сверку (из Transaction ID / из комментария), нет транзакции ни в одном поле. Колонку B можно вставить в столбец нужного дня.
- **`Источник`**: пустой лист. Сюда нужно вставить ответ админки перед запуском второго макроса.
- В сообщении указано, сколько строк попало на `Фильтр`, сколько на проверку и сколько отброшено.

## 6. Approved_Перенос2_v3

Файл: `macros/Approved_Transfer2_v3.bas`, версия 3.1.0. Второй шаг пары Approved.

**1) Название.** `Approved_Перенос2_v3`, перенос ответа админки и сверка.

**2) Функция.** Переносит данные админки с листа `Источник` (колонки «Номер заказа», «Сумма пополнения», «Статус», «ID пользователя», «ID субагента») в ADM-колонки листа `Фильтр`. Перенос идёт **по порядку строк**: 1-я строка `Источника` ложится на 1-ю строку `Фильтра`. Затем оставляет только тикеты, где статус не «Отказ» и не «В очереди» и где совпадают Transaction ID, User ID, сумма и Subagent ID.

**3) Что происходит с выгрузкой.**
- Нужны листы `Источник` и `Фильтр` от первого шага. Если число строк в них разное, макрос предупредит: строки могли съехать, и часть тикетов отсеется при сверке.
- Не прошедшие сверку строки удаляются. Оставшиеся раскладываются на два листа по колонке «Источник номера», а лист `Фильтр` удаляется:
  - **`Из выгрузки`**: номер стоял в колонке Transaction ID. Кнопки копируют Ticket ID и отдельно Transaction ID;
  - **`Из комментария`**: номер подобран из комментария. Одна кнопка копирует пары «Ticket ID + Transaction ID» для Bulk Approve, колонка `Transaction status` скрыта.
- Если `Фильтр` собран старой версией без колонки «Источник номера», разделения нет: результат остаётся на `Фильтре` с кнопками.
- Строки 14–15 листа `Отчёт` («после второго макроса») эта версия **не заполняет**, см. замечание в конце.

## 7. Monitoring_Цепочек_Статусов

## 8. Monitoring_Перемещение_тикетов

Файл: `macros/Monitoring_TicketMovements.bas`.

**1) Название.** `Monitoring_Перемещение_тикетов`, маппинг цепочек статусов (перемещения тикетов). Автор в коде: Dilmurat.

**2) Функция.** Считает по дням **отчётного месяца**, сколько тикетов L2 перешло по каждой нужной цепочке «Начальный статус → Конечный статус». Отчётная дата всегда вчерашняя:
- 01.10 строится сентябрь по 30.09 включительно;
- 02.10 строится октябрь по 01.10;
- 01.11 строится октябрь по 31.10.

Год, месяц и день берутся из заголовков выгрузки (строки 2, 3 и 4), поэтому одинаковые номера дней разных месяцев не смешиваются. Учитываются только строки блока «L2» с количеством тикетов.

**3) Что происходит с выгрузкой.**
- Исходный (активный) лист не меняется. Раскладка: A — Ответственность, B — начальный статус, C — конечный статус, D — тип строки, с E — значения по дням.
- После выгрузки создаётся **`Маппинг_Цепочек`**: колонка «Цепочка», дальше по колонке на каждый день отчётного месяца. Три блока:
  - **Обработка Team B (BT M)**, Mena 1x и Mena Leads 1x: 11 цепочек (Received / Received (Fraud) / Approved / CTAA → In Progress; In Progress → Sent for processing / Credited / Credited (Fraud) / Create new transaction / Approved by agent / CTTA by agent / Adjusted the amount (d));
  - **Обработка Team A,B (API)**: 4 цепочки из «Ожидает ответ от ПС» (→ Запрос информации / Ответ игроку / В работе / Требуется помощь поддержки);
  - **Обработка Team A,B (PSP)**: 4 цепочки из «Проверка транзакции» (те же конечные статусы).
- Если данных нет, ставится 0. У каждого блока своя кнопка «Копировать» на все дни блока.

## 9. Monitoring_TTR_FTT

Файл: `macros/Monitoring_TTR_FTT.bas`.

**1) Название.** `Monitoring_TTR_FTT`, медианы Time to Resolve / First Touch Time по странам.

**2) Функция.** Для каждого ГЕО считает **медиану по его рефералам**: каждый реферал имеет одинаковый вес, количество тикетов не учитывается. Метрика: `time_to_resolve_hms_med`, `first_touch_hms_med` или старая `med_dt_prev_diff_emp_sec_hms`. Если рядом в объединённой ячейке есть точное значение в секундах («Медианное first touch time» / «Медианное time to resolve»), берётся оно. Результат выстраивается в порядке 36 стран рабочей таблицы. Названия стран сравниваются без учёта регистра, вида тире и латинских букв, похожих на кириллицу.

**3) Что происходит с выгрузкой.**
- Данные берутся **со второго листа** книги (на первом средние, на втором медианы). Сам лист не меняется.
- Макрос останавливается с сообщением, если второго листа нет, если второй лист — сам результат, если колонки страны и метрики не в одной строке заголовков, если в заголовке сразу две метрики (оставьте одну, FTT или TTR), а также при ошибке в ячейке, времени без ГЕО или некорректном времени (с адресом ячейки).
- Лист **`Упорядоченный список`** создаётся сразу после второго листа, а если уже есть, обновляется на месте (перезаписываются колонки A:B). A — 36 стран (Азербайджан … Ямайка), B — время в формате `[h]:mm:ss`. Если страны нет, ячейка пустая.
- Кнопка «Копировать» в B1 копирует `B2:B37`. Обработчик кнопки (`TTR_FTT_CopyBlock`) теперь внутри модуля, отдельный `CMB_CopyBlock` больше не нужен.

## 10. Monitoring_Фильтрация

## 13. Monitoring_Переключения_Сотрудников

Файл: `macros/Monitoring_EmployeeSwitches.bas`. Версия не менялась.

**1) Название.** `Monitoring_Переключения_Сотрудников`, переключения сотрудников по дням.

**2) Функция.** То же для выгрузки переключений, но сумма за день (день + ночь) считается по сотруднику **со всех его столов**. Эта общая сумма выводится в каждую строку сотрудника, чтобы последующая синхронизация (`fillSwitchData()`) не перезаписала её данными только с последнего стола.

**3) Что происходит с выгрузкой.**
- Читается лист **`Sheet 1`**, он не меняется. Раскладка отличается от эффективности: A — Стол, B — Имя, с C — дни (номер дня в 4-й строке, смена в 5-й, данные с 6-й).
- В конце книги создаётся лист **`Преобразованные данные`**: Стол специалиста (переключения) / Имя специалиста (переключения) / 1…31.
- Нулевая сумма остаётся пустой ячейкой. Если у сотрудника несколько столов, одна и та же сумма стоит в каждой его строке, поэтому складывать эти строки между собой нельзя.
- В конце появляется сообщение «Преобразование завершено!».

`CMB_CopyBlock` из библиотеки удалён: новая версия `Monitoring_TTR_FTT` обрабатывает свою кнопку сама.
