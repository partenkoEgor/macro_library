# Расшифровка макросов для выгрузок

Актуально на 20.10.2026, сверено с кодом в `macros/`.

## Общее для всех макросов

- **Исходная выгрузка не меняется.** Ни один макрос не пишет в лист с исходными данными. Результат всегда появляется на новых листах.
- **Листы результата пересоздаются при каждом запуске.** Старый лист с тем же именем удаляется (или очищается целиком, как `Результат`), поэтому хранить на нём свои данные нельзя.
- **Кнопки «Копировать»** копируют только нужный блок значений, без заголовков и итоговых строк, чтобы его можно было сразу вставить в рабочую таблицу.
- Пороги «Nч+» считаются как «N часов и больше».

## 1. Monitoring_Нагрузка

Файл: `macros/Monitoring_Load.bas`

**1) Название.** `Monitoring_Нагрузка`, объединённый макрос нагрузки и зависших тикетов. Он заменил старые отдельные макросы `Нагрузка_API`, `Общая_нагрузка_PSP`, `Общий_мониторинг_BT_M_SMP`, `Monitoring_Зависшие_L1`, `Нагрузка_и_зависшие_Fraud` и `Зависшие_по_Гео`.

**2) Функция.** По одной общей выгрузке (лист `Report`) за один запуск считает всю нагрузку и все зависшие тикеты по API, PSP, BT M, SMP M, L1 и Fraud, а также готовит цифры для промежуточных отчётов (12:00 и 19:00) и текст вечернего отчёта. Фильтры пресетов (департаменты Mena 1x / Mena Leads 1x / Buffer, Ticket type, Agent ID, списки гео и рефералов) повторяются в коде, поэтому выгрузку не нужно заранее фильтровать.

**3) Что происходит с выгрузкой.**
- Лист `Report` не меняется. Если его нет, макрос останавливается с сообщением.
- Создаётся лист **`Фильтрация`**: 26 нужных колонок из `Report`. В `From` значение `Through customer support` заменяется на `PS`, а `By yourself` на `User`. `Processing time` пересчитывается в часах от **самой поздней `Processing date` в файле**, а не от текущего времени, поэтому результат не зависит от того, когда запущен макрос. Если в `Report` нет обязательной колонки, макрос показывает их список и останавливается.
- По листу `Фильтрация` строятся листы:

| Лист | Что на нём |
|---|---|
| `Нагрузка L2` | API Team B и Team A: депозиты и выводы по статусам New / Information provided / Review of stalled request / Awaiting response from PS / In progress / Individual agreement, плюс Buffer. PSP: депозиты и выводы по 5 статусам. BT M Mena 1x и Mena Leads 1x: 7 статусов (Received 189, Received (Fraud) 236, Approved 177, Create new transaction 251, Credited to another account 179, Revision needed 238, In progress 240). BT M L2/L1: 7 депозитных статусов (183 / 187 / 193 / 195 / 197 / 201 / 255) по 14 гео, агент `BankTransferAgent #279`. SMP M: 7 статусов по 12 гео. |
| `Нагрузка L1` | BT M, Agent ID 279, Mena 1x и Mena Leads 1x, 22 гео: депозитные и выводные статусы L1, а также PT 24 ч / 48 ч. |
| `Нагрузка Fraud` | Mena 1x и Mena Leads 1x: нагрузка и зависшие от 24 ч по 5 фрод-статусам (User spamming, Two users, Fake file, Fake file (Fraud), Revision needed (Fraud)) и блок «Ожидание пользователей» (Awaiting BS, Awaiting video). |
| `Зависшие тикеты` | BT M Mena 1x и Mena Leads 1x: Not Received 48h+, Sent for processing 72h+, New request 72h+, In Progress 24 ч, ПК 12 / 24 / 48 ч. SMP M: Sent for processing 72h+, New request 72h+, In progress 24 ч, PT 12 / 24 ч. Ниже блоки API, API без гео L1 и PSP: In progress / New / Customer provided additional info / Revising 12ч+ и 24ч+. |
| `ЗТ по ГЕО BT M,SMP M,PSP` | Зависшие от 24 ч по гео отдельно для BT M, PSP и SMP M, а также разбивка по статусам и рефералам. |
| `ЗТ по ГЕО API` | Гео-таблица API / PSP (36 гео, 70 связок «гео + реферал»), блок «не наши гео / рефералы» и список тикетов. |
| `Сводная` | 5 чисел для промежуточного отчёта 12:00 и 19:00 МСК: BT M (M1x), BT M (ML1x), API Team A, API Team B, PSP Team B. |
| `Вечерний отчет` | Готовый текст вечернего отчёта для чата. Справа от «/» стоят вечерние цифры, их считает макрос. Слева стоят «0», их нужно заменить утренними значениями вручную. Строки «Дата», «Создано тикетов», «Выводы», «Чат 72», «Ожидают ответа», «Массовый Approved», «Ошибка - Статус» заполняются вручную. |

- Листы расставляются по порядку: `Report`, `Фильтрация`, `Вечерний отчет`, `Сводная`, `Нагрузка L2`, `Нагрузка L1`, `Нагрузка Fraud`, `Зависшие тикеты`, `ЗТ по ГЕО API`, `ЗТ по ГЕО BT M,SMP M,PSP`. В конце открывается `Нагрузка L2` и появляется сообщение со списком созданных листов.
- У каждого блока есть кнопка «Копировать». Итоговые строки видны на листе, но в копирование не входят.

## 2. Monitoring_API_BT_M_PSP_SMP

Файл: `macros/Monitoring_API_BT_M_PSP_SMP.bas`

**1) Название.** `Monitoring_API_BT_M_PSP_SMP`, общий мониторинг количества тикетов по направлениям API, BT M, PSP и SMP.

**2) Функция.** Считает тикеты по каждому направлению в разрезе департаментов, тем (депозит / вывод), источника обращения (User / PS), VIP, гео и рефералов. Отбор по `Ticket type`: `API`, `BT M`, `PSP`, `SMP M` (для SMP дополнительно агент SendMePay). Правила исключения:
- Haiti, Dominican Republic, Costa Rica и Papua New Guinea не считаются нигде;
- Rolsbet исключён из BT M, а в API исключена только связка «Египет + Rolsbet»;
- Paraguay не считается в BT M (перешёл в SMP), Tunisia не считается в PSP;
- в API рефералы `in.1xbet.com` и `rolsbet` учитываются только для Турции, `1xbet.latam` только для Ямайки (способ оплаты Lynk) и Гватемалы (GT Continental, Banrural, Banco Industrial, BAC, Zigi);
- в BT M и SMP учитываются только страны из согласованных списков;
- VIP: `Type` = VIP, VIP-casino или VIP-hybrid.

**3) Что происходит с выгрузкой.**
- Активный лист с **сырой** выгрузкой не меняется. Запускать нужно именно на сырой выгрузке: макрос ищет в `From` значение `by customer`, а на листах `Filtered` / `Фильтрация`, где `From` уже заменён, все тикеты будут посчитаны как PS.
- Создаются 4 листа по порядку: **`API`**, **`BT M`**, **`PSP`**, **`SMP`**. На каждом:
  - сводка «Депозиты (User / PS), Выводы (User / PS), VIP, ИТОГО» по колонкам департаментов: на API это MENA 1x, Mena Leads 1X, Buffer; на BT M это MENA 1x и Mena Leads 1X; на PSP и SMP только MENA 1x;
  - блок GEO (API 36 стран, BT M 34, PSP 5, SMP 12);
  - блок рефералов;
  - кнопки «Копировать» над каждой колонкой сводки (без строки ИТОГО), над GEO и над рефералами.
- Если для листа не найдена нужная колонка (`Payment method` для API, `Agent` для SMP), этот лист не создаётся, но в конце всё равно может появиться «Готово!».

## 3. Monitoring_SFP_SMP_NR72ч

Файл: `macros/Monitoring_SFP_SMP_NR72h.bas`

**1) Название.** `Monitoring_SFP_SMP_NR72ч`, тикеты, зависшие от 72 часов в статусах Sent for processing и New request (BT M и SMP).

**2) Функция.** Находит тикеты, которые висят 72 часа и больше:
- BT M: статусы `Sent for processing (M)` и `New request (M)`;
- SMP: статусы `Sent for processing` и `New request`, только Agent ID = `1014`, страны Egypt / Mauritania / Sudan и 14 разрешённых рефералов.

Считает количество по SMP и собирает все списки на одном листе для копирования.

**3) Что происходит с выгрузкой.**
- Исходный лист не меняется. Если запустить макрос с одного из итоговых листов, он попросит перейти на лист выгрузки.
- Создаётся **`Filtered`**: 23 колонки (включая `Agent ID` и `Referal`), `From` → `PS` / `User`, `Processing time` в часах **от текущего времени** (`Now`), автофильтр.
- Создаются листы со списками «Гео / Ticket ID / Subagent»: **`SFP (M) 72h+`**, **`New request (M) 72h+`**, **`SMP SFP 72h+`**, **`SMP NR 72h+`**.
- **`SMP подсчет 72h+`**: счётчики SMP Sent for processing 72h+, SMP New request 72h+ и SMP Total 72h+.
- **`Для копирования`**: все четыре списка один под другим. Если тикетов нет, в блоке написано «Нет тикетов».
- Поскольку время считается от `Now`, результат зависит от времени запуска.

## 4. Monitoring_Выводы

Файл: `macros/Monitoring_Withdrawals.bas`

**1) Название.** `Monitoring_Выводы`, мониторинг выводов BT M и SMP M.

**2) Функция.** Считает выводы Mena 1x и Mena Leads 1x по статусам:
- BT M (тип `BT M`, агент BankTransfer…): 238 Review required, 205 Money not sent, cancel, 175 Adjust payment amount, 185 Limit reached on the recipient side, 191 Recipient details incorrect, 199 Request for payment statement, 203 Sent. Статусы 185 / 191 / 199 / 203 считаются только по 13 странам (Azerbaijan, Afghanistan, Bolivia, Guatemala, Honduras, Iran, Canada, Nicaragua, Panama, Paraguay, Taiwan, Kyrgyzstan, Jamaica). Остальные статусы считаются по всем странам.
- SMP M (тип `SMP M`, агент SendMePay): 81 Revision needed, 53 Money not sent, cancel, 38 Adjust the payout amount.

Старые названия статусов тоже распознаются. Отдельно собираются Ticket ID отклонённых транзакций.

**3) Что происходит с выгрузкой.**
- Исходный лист не меняется. Если запустить с листа `Результат` или `Фильтр`, макрос попросит перейти на лист выгрузки.
- Создаётся **`Фильтр`**: только подходящие тикеты, 15 колонок (Department, Ticket type, External Status, From, Transaction Status, Transaction ID, Check amount, Subagent, Payment date, пустая колонка-разделитель, Ticket ID, Country, Processing time, Internal comment, Agent). Тикеты с `Transaction Status = rejected` стоят сверху. `From`: `Through Customer Support` → `L1`, `By yourself` → `User`. `Payment date` приводится к дате. Кнопка в `K1` копирует Ticket ID отклонённых тикетов.
- Создаётся **`Результат`**: BT M (общая сумма в B4 и 7 статусов в B5:B11) и SMP M (общая сумма в B16 и 3 статуса в B17:B19). Кнопки копируют `B5:B11` и `B17:B19`, общие суммы в копирование не входят.

## 5. Monitoring_Фильтрация

Файл: `macros/Monitoring_Filtering.bas`

**1) Название.** `Monitoring_Фильтрация`, старый отдельный макрос подготовки выгрузки. Его логика сейчас встроена в `Monitoring_Нагрузка` (лист `Фильтрация`) и `Monitoring_SFP_SMP_NR72ч` (лист `Filtered`).

**2) Функция.** Оставляет из выгрузки заявок только нужные колонки в рабочем порядке, приводит `From` к коротким значениям и считает, сколько часов тикет находится в обработке.

**3) Что происходит с выгрузкой.**
- Исходный лист не меняется.
- Создаётся лист **`Filtered`** (вставляется перед активным листом): 21 колонка (Date created, Processing date, Processing time, From, External Status, Country, Ticket ID, Transaction ID, User ID, Check amount, Ticket currency, Subagent ID, Subagent, Agent's wallet, User wallet, Unique transfer number, Topic, Ticket type, Department, Agent, Internal comment). Если колонки в выгрузке нет, она создаётся пустой.
- `Internal comment` стоит последней, её ширина 20.
- `From`: `Through customer support` → `PS`, `By yourself` → `User`.
- `Processing time` = часы от `Processing date` до текущего момента (`Now`), округлено до сотых.

## 6. Monitoring_Цепочек_Статусов

Файл: `macros/Monitoring_StatusChains.bas`

**1) Название.** `Monitoring_Цепочек_Статусов`, медианное время перехода по статусам BT M.

**2) Функция.** Из сводной таблицы с колонками «Начальный статус» и «Медианное время перехода» берёт общее значение (строка Grand Total / Общий итог / Итого) и медиану по 13 статусам: Received 189, Received (Fraud) 236, Approved 177, Create new transaction 251, Credited to another account 179, Revision needed 238, Higher quality and resolution file 183, Not Received 187, Refund details needed 193, Request a statement for deposit 195, Request deposit screenshot 197, Returned to sender's account 201, File does not match ticket 255. В выгрузке статусы на русском, на выходе подписи на английском с ID.

**3) Что происходит с выгрузкой.**
- Исходный лист не меняется. Источник — активный лист. Если активен `Результат`, макрос ищет первый лист с заголовком «Начальный статус».
- Лист **`Результат`** создаётся или очищается целиком: B2 «Общее», B3 «% изменения» (остаётся пустой, заполняется вручную), B5:B17 13 статусов. Время в формате `[h]:mm:ss`.
- Если всё найдено, диапазон `B2:B17` сразу копируется в буфер. Вставлять его нужно начиная с ячейки «Общее».
- Если статус не найден или время некорректное, ячейка подсвечивается красным, появляется список ошибок и диапазон в буфер **не** копируется.

## 7. Monitoring_Перемещение_тикетов

Файл: `macros/Monitoring_TicketMovements.bas`

**1) Название.** `Monitoring_Перемещение_тикетов`, маппинг цепочек статусов (перемещения тикетов). Автор в коде: Dilmurat.

**2) Функция.** Считает по дням месяца, сколько тикетов L2 перешло по каждой нужной цепочке «Начальный статус → Конечный статус». Берёт только блок «L2» и только строки с количеством тикетов. Считаются дни с 1-го по **вчерашний** (сегодняшний день неполный).

**3) Что происходит с выгрузкой.**
- Исходный (активный) лист не меняется. Ожидаемая раскладка: A — Ответственность (Не L2 / L2), B — начальный статус, C — конечный статус, D — тип строки, с E — значения по дням, номера дней в 4-й строке.
- Сразу после выгрузки создаётся лист **`Маппинг_Цепочек`**: колонка «Цепочка», дальше по колонке на каждый день. Три блока:
  - **Обработка Team B (BT M)**, Mena 1x и Mena Leads 1x: 11 цепочек (Received / Received (Fraud) / Approved / CTAA → In Progress; In Progress → Sent for processing / Credited / Credited (Fraud) / Create new transaction / Approved by agent / CTTA by agent / Adjusted the amount (d));
  - **Обработка Team A,B (API)**: 4 цепочки из «Ожидает ответ от ПС» (→ Запрос информации / Ответ игроку / В работе / Требуется помощь поддержки);
  - **Обработка Team A,B (PSP)**: 4 цепочки из «Проверка транзакции» (те же конечные статусы).
- Если данных по цепочке нет, ставится 0. У каждого блока своя кнопка «Копировать», она копирует все дни блока.
- Если запустить 1-го числа, лист получится пустым (дней «по вчера» нет).

## 8. Monitoring_TTR_FTT

Файл: `macros/Monitoring_TTR_FTT.bas`

**1) Название.** `Monitoring_TTR_FTT`, медианы Time to Resolve / First Touch Time по странам.

**2) Функция.** Берёт медианное значение метрики (`time_to_resolve_hms_med`, `first_touch_hms_med` или старую `med_dt_prev_diff_emp_sec_hms`) по каждой стране и выстраивает 36 стран в фиксированном порядке рабочей таблицы. Названия стран сравниваются без учёта регистра, вида тире и латинских букв, похожих на кириллицу.

**3) Что происходит с выгрузкой.**
- Данные берутся **со второго листа** книги (на первом средние значения, на втором медианы). Сам лист не меняется. Если второго листа нет или на нём нет нужных колонок, макрос останавливается с сообщением.
- Сразу после второго листа создаётся **`Упорядоченный список`**: A — 36 стран (Азербайджан … Ямайка), B — значение в формате `[h]:mm:ss`. Если страны нет в выгрузке, ячейка пустая.
- Кнопка «Копировать» в B1 копирует `B2:B37` (через `CMB_CopyBlock`).

## 9. Monitoring_Переключения_Агентов

Файл: `macros/Monitoring_AgentSwitches.bas`

**1) Название.** `Monitoring_Переключения_Агентов`, переключения по столам, гео и рефералам.

## 10. Monitoring_Эффективность_Сотрудников

Файл: `macros/Monitoring_EmployeeEfficiency.bas`

**1) Название.** `Monitoring_Эффективность_Сотрудников`, эффективность сотрудников по дням.

**2) Функция.** Разворачивает выгрузку эффективности с разбивкой «день / ночь» в плоскую таблицу «сотрудник × день месяца». Если за одну дату есть и дневная, и ночная смена, значения складываются. Строки `total` пропускаются.

**3) Что происходит с выгрузкой.**
- Читается лист **`Sheet 1`**, он не меняется. Раскладка: A — Команда, B — Стол, C — Имя, с D — дни; номер дня в 4-й строке, смена («день» / «ночь») в 5-й, данные с 6-й строки.
- В конце книги создаётся лист **`Преобразованные`**: Команда / Стол специалиста / Имя специалиста / 1…31. Одна строка на каждую строку сотрудника из выгрузки. Пустые дни остаются пустыми.
- Сообщения о завершении нет.

## 11. Monitoring_Переключения_Сотрудников

Файл: `macros/Monitoring_EmployeeSwitches.bas`

**1) Название.** `Monitoring_Переключения_Сотрудников`, переключения сотрудников по дням.

**2) Функция.** То же для выгрузки переключений, но сумма за день считается по сотруднику **со всех его столов** (день + ночь), и эта общая сумма выводится в каждую строку сотрудника. Так последующая синхронизация (`fillSwitchData()`) не перезапишет сумму данными только с последнего стола.

**3) Что происходит с выгрузкой.**
- Читается лист **`Sheet 1`**, он не меняется. Раскладка отличается от эффективности: A — Стол, B — Имя, с C — дни (номер дня в 4-й строке, смена в 5-й, данные с 6-й).
- В конце книги создаётся лист **`Преобразованные данные`**: Стол специалиста (переключения) / Имя специалиста (переключения) / 1…31.
- Нулевая сумма остаётся пустой ячейкой. Если у сотрудника несколько столов, одна и та же сумма стоит в каждой его строке, поэтому складывать эти строки между собой нельзя.
- В конце появляется сообщение «Преобразование завершено!».

## 12. CMB_CopyBlock

Файл: `macros/CMB_CopyBlock.bas`

**1) Название.** `CMB_CopyBlock`, обработчик кнопки «Копировать».

**2) Функция.** Вспомогательная функция, вручную не запускается. Её вызывает кнопка «Копировать», которую создаёт `Monitoring_TTR_FTT`: функция копирует диапазон, адрес которого записан в кнопке. В списке макросов (Alt+F8) не отображается.

**3) Что происходит с выгрузкой.** Ничего: данные не меняются, нужный диапазон листа `Упорядоченный список` просто копируется в буфер обмена, а в строке состояния Excel появляется подтверждение. Если `CMB_CopyBlock` уже есть в вашей книге или `PERSONAL.XLSB`, этот модуль импортировать не нужно.
